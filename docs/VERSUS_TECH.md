# 奶娃峡谷技术选型

核对日期：2026-10-27。当前目标是 3v3 客户端，不改已有游戏服务器和生产网络。

| 层 | 选择 | 原因与当前状态 |
| --- | --- | --- |
| 客户端界面 | TypeScript + Vite + DOM/CSS | 本批已采用。复用项目构建、资源预加载、离线与更新；选角状态用纯函数 reducer，便于验证，不需要为了四页菜单引入一套大框架。 |
| 后续战斗画面 | Babylon.js | 项目已有 9.32.0 依赖，逃生已使用。适合固定俯视真 3D、光照、动画与模型；峡谷战斗本批未创建。 |
| 后续权威房间 | Colyseus（候选） | TypeScript/Node 房间生命周期、状态同步可减少重复造轮子。只对候选做选型，尚未安装、开放房间或替换现有逃生 WSS。 |
| 复杂阶段流 | XState（备选） | 等真正加入组队、重连、选角阶段与对局生命周期后再引入；现在本机编队 reducer 已足够。 |
| 多段界面动画 | GSAP（备选） | 长时间轴、进场编排需要时使用。当前只有短 CSS 过渡并尊重减少动态效果设置。 |
| 纯 2D 战斗备选 | Phaser | 适合 WebGL/Canvas 2D 精灵游戏；如果明确转为纯 2D 才考虑。当前希望保留真 3D，不另塞第二个渲染引擎。 |

不需要先把界面全部改写 React/Vue。等真实客户端复杂度明显增加，可将独立 versus 模块逐步迁移；不让实验模式拖累现有浴场/逃生。

## 建议的未来运行分工（未实现）

浏览器逐帧渲染、摄像机、输入采样、局部表现与移动预测；专用服务器推进规则时间、校验位置/技能/命中、决定共享结果并推送快照。固定模拟 tick 与插值刷新率分开，不逐帧请求 HTTP，也不依赖房主浏览器裁决所有命中。具体 tick、带宽、房间预算应实测，不虚报单局成本。

现有 Express/WSS 继续负责逃生。未来峡谷房间应独立模块与资源预算、版本协议、限流和测量，经过负载与延迟模拟再决定是否采用 Colyseus；本批没有修改服务器路径、容器编排、共享网络或 LAN 开发。

## 官方资料

- [Babylon.js](https://www.babylonjs.com/)：Web 3D 引擎与工具。
- [Colyseus 房间](https://docs.colyseus.io/room)与[状态同步](https://docs.colyseus.io/state)：房间生命周期、服务端状态与客户端同步。
- [XState](https://stately.ai/docs)：状态机和 actor 模型。
- [GSAP](https://gsap.com/docs/v3/)：动画时间轴与控制。
- [Phaser 官方文档](https://www.phaser.io/oss/docs)：JavaScript/TypeScript 的 2D Web 游戏框架。

本批引入运行时依赖：**0**。新增源代码经现有 Vite 动态分包，仅进入峡谷后加载界面模块；原画按用户要求保留生成 PNG 原尺寸与原字节，并进入离线预缓存。
